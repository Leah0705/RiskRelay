> from an actual run on the hardware and command stated. The sections after it
> are written by hand: the sweep and thread-setting numbers come from re-running
> the same command (fresh server each run), and the scaling section is analysis.
> Re-running the script rewrites the generated part and drops the rest.

## Environment

- **Date:** 2026-10-13 16:49
- **Hardware:** Linux cloud container, Intel Xeon @ 2.10GHz, 2 vCPU, 7.8 GB RAM
- **Python:** 3.13.16
- **Feature store backend:** in-memory fallback (single process)
- **Server:** uvicorn 1 worker

## Command

```bash
python loadtest/loadtest.py --host http://127.0.0.1:8010 --accounts 2000 --warmup-per-account 5 --requests 20000 --concurrency 8
```

## Workload

- Warmed store with **10,000** events (2,000 accounts × 5 each).
- Drove **20,000** store-backed `/score` requests (each also commits, i.e. score-then-ingest) at concurrency **8**.

## Concurrency sweep (same box, single worker)

Same command at each concurrency, `n_jobs=1` on the serving path, fresh server
per run:

| Concurrency | Throughput | p50 | p99 | Errors |
|---|---|---|---|---|
| 1 | 171 RPS | 5.5 ms | 9.9 ms | 0 |
| 4 | 209 RPS | 18.1 ms | 35.1 ms | 0 |
| 8 | 199 RPS | 37.9 ms | 76.0 ms | 0 |
| 12 | 206 RPS | 55.0 ms | 127.9 ms | 0 |
| 64 | 139 RPS | 312.3 ms | 2054.4 ms | 15 (0.07%) |

Throughput plateaus near 200 RPS from concurrency 4 onward. Past that point,
extra in-flight requests only wait in the queue in front of the single worker,
so latency grows with concurrency while throughput stays flat. Concurrency 12
already breaks the 100 ms p99 target, and concurrency 64 shows the saturation
failure mode, with timeouts included.

**Read the headline p50 as queue time.** The concurrency-1 row shows what one
request costs: 5.5 ms at p50 end to end, of which XGBoost inference is about
1.5 ms (`reports/model_latency.json`). The rest is HTTP, the feature-store read,
the commit and serialization, plus a load generator competing for the same two
cores. The headline p50 of 37.9 ms is that same work with seven other requests
queued ahead of it, so it does not describe the time it takes to score an event.

### Serving thread setting: `n_jobs=1` vs as trained

`MODEL.serving_n_jobs` pins XGBoost inference to one thread at model load
(`src/api.py`). The same command with the setting removed, so the model keeps
its training-time `n_jobs=-1`:

| | Concurrency 1 | Concurrency 8 |
|---|---|---|
| `n_jobs=-1` (as trained) | 158 RPS, p99 12.9 ms | 204 RPS, p99 75.4 ms |
| `n_jobs=1` (serving) | 171 RPS, p99 9.9 ms | 199 RPS, p99 76.0 ms |

On this 2-vCPU box the pinned setting is slightly faster at concurrency 1 and
indistinguishable at concurrency 8. With only two cores, the thread pool of a
single request has little room to contend, so the box cannot show the
oversubscription the setting is meant to prevent. The case for `n_jobs=1` is
the multi-worker one: with one uvicorn worker per core, a worker whose
inference claims every core contends with its neighbours. That argument is
design reasoning and has not been benchmarked here; a run on a machine with
more cores and several workers would test it.

## How this scales in production (not benchmarked here)

The numbers above come from **a single uvicorn worker with the in-memory
store**, sharing two vCPUs with the load generator. The intended production
configuration removes the single-process ceiling:

- **N workers behind the load balancer**, about one per core. For this
  CPU-bound workload throughput should grow with cores, which is what pinning
  serving to `n_jobs=1` is for: each worker uses one core for inference.
- Multiple workers need **shared state**, which the Redis backend provides (the
  in-memory store is per-process). `tests/test_streaming_parity.py` proves the
  Redis path computes the same features as batch, and `docker-compose.yml` brings
  it up, but its throughput has not been measured.
- On this box, a single-threaded micro-benchmark against a local Redis 7 server
  (2,000 warmed accounts, 3,000 events) measured `get_features` at 0.30 ms p50
  (0.61 ms p99) and `commit` at 0.16 ms p50 (0.35 ms p99), against 0.005 ms for
  the in-memory read. Redis therefore adds about 0.45 ms to a 5.5 ms request at
  p50. That figure is a micro-benchmark; it is not a load test of the Redis
  path.

Further headroom if needed: batch inference across in-flight requests,
serialize the feature row in C, and keep SHAP (`explain=true`) off the hot path
(it already defaults off).
